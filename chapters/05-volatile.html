5  原子性と可視性

5.1 概要

チャプター 4 では、競合状態という問題を、synchronized による排他制御で防ぎました。 この章では、排他制御によって何が保証されていたのかを、原子性と可視性という2つの性質に分けて整理します。

そのうえで、可視性だけを保証する volatile 修飾子を学び、volatile では競合状態を防げない理由を説明します。

5.2 問題・目的・手段の関係

第4章の内容は、「問題」「目的」「手段」の3つの関係として整理できます。

区分 名前 内容
問題 競合状態 複数のスレッドが共有変数を同時に更新し、更新の一部が失われる
目的 原子性 一連の操作を、途中で他のスレッドに割り込まれずに行う
手段 排他制御 synchronized を使い、その処理を同時に1つのスレッドだけに実行させる

原子性とは

原子性とは、操作の途中に他のスレッドが割り込めない性質です。 「原子」という言葉は、「それ以上分けられないもの」という意味で使われています。

セクション 4.3 で見たとおり、c++ は「読み込み・計算・書き込み」の3つの操作に分かれるため、原子性がありません。 そのため 図 4.1 のように、スレッド1の読み込みと書き込みの間にスレッド2が割り込み、更新が失われました。

つまり、競合状態は、原子性のない操作を、複数のスレッドが同時に行うことで起こる問題です。 逆に、c++ の3つの操作を原子的に（途中で割り込まれずに）行うことができれば、競合状態は起こりません。 したがって、原子性は、競合状態を防ぐために達成すべき目的です。

排他制御は原子性を実現する手段

Javaでは、c++ と書いただけでは原子性は得られません。そこで セクション 4.4 では、c++ を synchronized で囲みました。

  • ロックを持つスレッドが3つの操作をすべて終えるまで、他のスレッドは同じロックを使う処理に入れません。
  • その結果、他のスレッドから見ると、3つの操作がまとめて一度に行われたように見えます。

このように、排他制御は、原子性を実現するための手段です。

5.3 可視性

共有変数を複数のスレッドで扱うときには、競合状態とは別の問題もあります。 それは、あるスレッドが書き込んだ値が、他のスレッドからいつまでも見えないことがある、という問題です。

可視性とは、あるスレッドが書き込んだ値を、他のスレッドが読めることが保証される性質です。

問題の再現

次のプログラムでは、メインスレッドが1秒後に running を false にして、スレッド t に停止を指示します。 スレッド t は running が true の間だけループを続けるので、本来は1秒後に終了するはずです。

StopTest.java（volatileなし）
public class StopTest {
    public static void main(String[] args) throws InterruptedException {
        LoopThread t = new LoopThread();
        t.start();
        Thread.sleep(1000);   // 1秒待つ
        t.running = false;    // スレッド t に停止を指示する
        System.out.println("メイン：停止を指示しました");
        t.join();             // スレッド t の終了を待つ
        System.out.println("メイン：スレッド t が終了しました");
    }
}

class LoopThread extends Thread {
    boolean running = true;  // メインスレッドから false にされる（volatile を付けていない）

    public void run() {
        long n = 0;
        while (running) {
            n++;  // 何らかの処理
        }
        // running が false になれば、ループを抜けてスレッドが終了する
    }
}

実行すると、「メイン：停止を指示しました」と表示された後、プログラムが終わらないことがあります（Ctrl + C で停止してください）。 メインスレッドは確かに running を false にしたのに、スレッド t にはその書き込みが見えていないのです。

なぜ値が見えないのか

  • 各スレッドは、処理を速くするために、共有変数の値を一時的に手元（CPUのレジスタなど）に保持することがあります。
  • また、Javaの実行環境（JITコンパイラ）は、最適化のために、ループの中で変数を毎回読み込むのを省略し、最初に1回だけ読み込むように書き換えることがあります。
  • その結果、スレッド t は最初に読んだ true を使い続け、他のスレッドによる書き換えに気づきません。

図 4.1 と比べてください。図 4.1 では、2つのスレッドが最新の値を正しく読んだうえで、互いの操作の間に割り込んだことが問題でした。 一方、図 5.2 では割り込みは起きておらず、書き込まれた値が見えないことが問題です。 この2つは、原因の異なる別々の問題です。

synchronized は可視性も保証する

synchronized は、原子性だけでなく、可視性も保証します。 あるスレッドがロックを解放する前に書き込んだ値は、その後で同じロックを取得したスレッドから必ず見えます。

セクション 4.4 の Count が synchronized によって正しく30000になったのは、次の2つがどちらも保証されていたためです。

  • 原子性：「読み込み・計算・書き込み」の途中に、他のスレッドが割り込まない。
  • 可視性：ロックを取得したスレッドは、前にロックを持っていたスレッドが書き込んだ最新の値を読める。

5.4 volatile変数

volatile は、変数の可視性を保証する修飾子です。

  • volatile を付けた変数への書き込みは、すぐに他のスレッドから見えるようになります。
  • volatile を付けた変数を読み込むときは、常に最新の値が読まれます。手元に保持した古い値が使われたり、読み込みが省略されたりすることはありません。

前節の StopTest は、running に volatile を付けるだけで正しく終了するようになります。

StopTest.java（volatile版）の変更箇所
class LoopThread extends Thread {
    volatile boolean running = true;  // volatile を付ける
    // …（run メソッドは変更なし）
}

スレッド t は、ループのたびに running の最新の値を読むため、メインスレッドが false を書き込んだ後にループを抜けて終了します。

5.5 volatileでは競合状態を防げない

では、セクション 4.2 の Count の変数 c に volatile を付ければ、競合状態は防げるでしょうか。

Count.java（volatile版）の変更箇所
public class Count {
    volatile int c = 0;  // volatile を付ける（synchronized は使わない）
    // …（main メソッドと CounterThread クラスは4.2節と同じ）
}

実行すると、volatile を付けない場合と同じく、最終結果が30000未満になることがあります。

その理由は、図 4.1 をもう一度見るとわかります。

  • 手順2でスレッド2が読んだ10は、その時点での最新の値です。つまり、この図では可視性の問題は起きていません。
  • 問題は、スレッド1の「読み込み」と「書き込み」の間に、スレッド2が割り込んだことです。つまり、原子性がないことが原因です。
  • volatile は、1回1回の読み込み・書き込みで最新の値を使うようにするだけです。「読み込み・計算・書き込み」の3つの操作を、ひとまとまりにする働きはありません。

したがって、volatile を付けても、図 4.1 と同じ実行順は起こりえます。

重要volatile で競合状態を防げない理由
  1. 競合状態を防ぐには、原子性が必要である。
  2. volatile は可視性を保証するが、原子性は保証しない。
  3. したがって、volatile では競合状態を防げない。競合状態を防ぐには、synchronized による排他制御を使う。

5.6 volatile の用途

volatile だけで正しく扱えるのは、次の2つの条件を満たす変数です。

  • 1つのスレッドだけが書き込み、他のスレッドは読むだけである。
  • 書き込む値が、変数の現在の値に依存しない（running = false のような単純な代入であり、c = c + 1 のように「読んでから書く」操作ではない）。

代表例は、セクション 5.3.1 の running のような、スレッドを止めるためのフラグです。

ノート参考：AtomicInteger

カウンタのように「読んで、変えて、書く」変数を安全に扱うには、synchronized のほか、java.util.concurrent.atomic.AtomicInteger の incrementAndGet() を使う方法もあります。 incrementAndGet() は、1増やす操作を原子的に行うメソッドです。ロックを使わずに原子性と可視性を実現する仕組みになっています。

初めのうちは、次のように覚えておけば十分です。

  • 複数のスレッドから共有変数を書き換える処理にはsynchronized を使う。
  • volatile は、停止フラグのように「1つのスレッドが書き、他のスレッドは読むだけ」の場合にのみ使う。
